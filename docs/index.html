npu-unknown-unknown

A three-layer LLVM backend for a fully-programmable Neural Processing Unit. Every instruction is a 32-byte word — 8× the size of RISC-V — carrying complete operand context: tile dimensions, element counts, and a 64-bit immediate. Compiles LLVM IR to ELF .o files via three coordinated instruction streams.

Architecture

Three engines, one machine

One chip, three fully independent instruction streams running simultaneously. The Control Core sequences the other two — it DMA-stages data into SRAM, fires the Tensor Engine to run the matmul, then launches the Vector Core for per-element post-processing. A complete program is exactly two C arrays: cinst[] for layers 1+2 and vinst[] for layer 3.

The canonical pattern is: DMA_IN (DRAM → SRAM), WAIT, MMA over SRAM data, STORE result back to DRAM. This hides DRAM latency behind the DMA transfer.

Kernel launch — step by step

The control program prepares and fires a vector kernel like this:

control program: write args → launch → wait
; 1. Write kernel arguments to DRAM (host already did this, or do it here)
LI   x10, 0x1000        ; x10 = DRAM address where args live
LI   x11, 64            ; grid size = 64 instances

; 2. Register kernel index (done once in C via npu_register_kernel(0, vinst_arr, len))

; 3. Launch: kernel[0] runs 64 times, once per instance
KLAUNCH 0, x11          ; non-blocking — control core moves on immediately

; 4. Do other work here, or just wait:
KWAIT                    ; stall until all 64 instances hit KEXIT
HALT                     ; end control program
vector kernel entry — what the engine scalar registers hold on entry
; On entry to every kernel instance:
;   s0 = instance id  (0, 1, 2, … grid_size-1)
;   s1 = args base pointer in DRAM (the address written to x10 above)
;   vl = 0 (must call VSETVL before any vector op)

KID   s0               ; refresh s0 = this instance's id
SMULI s2, s0, 256      ; s2 = s0 × 256 (byte offset for this slice)
SADD  s3, s1, s2       ; s3 = args_base + offset = this instance's data ptr
SLI   s4, 256          ; s4 = 256 (element count)
VSETVL s5, s4          ; set vector length; s5 = actual vl granted
VLOAD v0, s3           ; load this instance's slice into v0
; … compute …
VSTORE v0, s3          ; write result back
KEXIT                  ; signal done — unblocks KWAIT in control core
Instruction Encoding

The 32-byte instruction word

Both cinst (control/tensor) and vinst (vector) instructions are exactly 32 bytes, zero-padded. Byte 0 is the stream-type discriminator. This fixed width makes the binary format trivially parseable and leaves room for future ISA extensions in the padding bytes [24–31].

Why 32 bytes?

The simulator's npu_encode_cinst() / npu_decode_cinst() in npu_asm.c define this format. The LLVM backend mirrors it exactly in NPUMCCodeEmitter.cpp. The instruction index used for branch targets is therefore byte_address / 32 — the ELF relocation stores this divided value, not a raw byte address.

Calling convention

Arguments are passed in x10–x17. Return value in x10. The call sequence: ADDI x2, x2, -N (frame setup), SW x1, 0(x2) (spill ra), JAL x1, callee, LW x1, 0(x2) (restore ra), ADDI x2, x2, N (frame teardown), JALR x0, x1, 0 (return).

JAL serves dual duty: JAL x1, callee is a call (link register = x1). JAL x0, label is an unconditional branch (link discarded to zero register). Both map to the same cop::JAL opcode. The LLVM backend uses NPU::JAL for calls and NPU::BR (a pseudo that also lowers to JAL) for unconditional branches.

LLVM intrinsics

Declared in llvm/include/llvm/IR/IntrinsicsNPU.td. All tile-mutating ops are IntrHasSideEffects so LLVM generates INTRINSIC_W_CHAIN nodes (which thread the memory chain), not INTRINSIC_WO_CHAIN. This is required for the LowerIntrinsicCall hook to intercept them.

example: 4×4×4 matmul in LLVM IR
define i64 @matmul(ptr %out, ptr %a, ptr %b) {
  ; tile register 0 is an i64 constant, not a physical reg
  %1 = call {i64, token} @llvm.npu.cfg.shape(i64 4, i64 4, i64 4)
  %2 = call {i64, token} @llvm.npu.acc.clr(i64 0)   ; tile 0
  %3 = call {i64, token} @llvm.npu.load(ptr %a, i64 1, i64 16)  ; tile 1
  %4 = call {i64, token} @llvm.npu.load(ptr %b, i64 2, i64 16)  ; tile 2
  %5 = call {i64, token} @llvm.npu.mma(i64 0, i64 1, i64 2)
  call void @llvm.npu.store(ptr %out, i64 0, i64 16)
  ret i64 0
}

Writing a result to DRAM

There is no vector-ISA scalar store instruction. To write a VREDSUM result back to DRAM, you must broadcast it first: VREDSUM s6, v0 → VBCAST v1, s6 → VSTORE v1, 0(s5). This is the only path from a reduction scalar to memory.

Binary Format

ELF encoding & relocations

NPU produces standard 64-bit ELF with a custom machine number and RELA-format relocations. A future NPU linker applies the branch-target formula; the assembler writes a zero placeholder.

Machine number
0x13b
EM_NPU = 315 decimal, defined in llvm/include/llvm/BinaryFormat/ELF.h after EM_LOONGARCH = 258
Relocation format
RELA
HasRelocationAddend = true. Addend is stored in the relocation record, not in the instruction bytes. Required for the ÷32 formula.
Fixup anchor offset
+16
MCFixup created at byte 16 within the 32-byte word — the start of the 8-byte imm field. r_offset in the RELA entry therefore points directly at the bytes being patched.

Verification

shell
llc -mtriple=npu-unknown-unknown -filetype=obj call.ll -o out.o
llvm-readelf -h out.o   # Machine: 13b
llvm-readelf -r out.o   # R_NPU_BRANCH at offset 0x50 → callee + 0
llvm-readelf -S out.o   # .rela.text section present

Offset 0x50 = instruction #2 (zero-indexed) × 32 bytes/instr + 16 bytes (imm field offset). In the caller function: ADDI is instruction 0 (0x00), SW is instruction 1 (0x20), JAL is instruction 2 (0x40) — its imm field starts at 0x40 + 16 = 0x50.

Design Decisions

Key choices & their rationale

Tile registers encoded as i64 SSA constants
Tile registers t0–t7 are not real machine registers in the LLVM sense — they are i64 constant values passed through the SSA chain. The SelectionDAG lowering extracts them with getTileConst(), which recursively follows INTRINSIC_W_CHAIN token operands to find the ConstantSDNode.
Avoids building a tile register allocator. The NPU tile register file is small (8 entries) and statically scheduled — spilling a tile register doesn't make sense in the model. Constants survive the entire compiler pipeline without allocation.
IntrHasSideEffects required for tile-mutating operations
ACC.CLR, MMA, LOAD, STORE — any op that mutates a tile register — must be marked IntrHasSideEffects in IntrinsicsNPU.td. Without this, LLVM creates INTRINSIC_WO_CHAIN nodes, which bypass the setOperationAction(ISD::INTRINSIC_W_CHAIN, MVT::i64, Custom) hook and reach the SelectionDAG unhandled.
The side-effect flag forces a memory/chain dependency edge, preventing the DAG from reordering or eliminating tile ops — necessary because tile state is shared mutable storage invisible to LLVM's alias analysis.
JAL opcode serves both calls and unconditional branches
The ISA has one direct-branch opcode: JAL. JAL x1, target is a call (link register x1 holds return address). JAL x0, target is an unconditional branch (link discarded to zero register). LLVM defines NPU::JAL for calls and NPU::BR for branches — both lower to cop::JAL in the binary emitter. The rd field distinguishes them at decode time.
Mirrors RISC-V's JAL/J encoding scheme. Simpler than adding a dedicated BR opcode: the same fixup infrastructure handles both, and the hardware decoder reads byte [2] (rd) to differentiate.
applyFixup must call maybeAddReloc — the missing link
MCAssembler::evaluateFixup() calls backend.applyFixup(F, Fixup, Target, Data, Value, IsResolved). For external symbols, IsResolved=false. The backend's applyFixup must call maybeAddReloc(F, Fixup, Target, Value, IsResolved) internally — without this, MCObjectWriter::recordRelocation() is never invoked and no ELF RELA entry is emitted. The object file appears to compile successfully but the relocation table is empty. The callee symbol shows as UND with value 0, and the JAL imm field is silently zeroed.
This is a non-obvious invariant. The call chain is: evaluateFixup → applyFixup → maybeAddReloc → recordRelocation → ELF RELA entry. Skipping maybeAddReloc produces no error, no warning — just a broken object file.
MCFixup created at offset 16 (the imm field), not offset 0
MCFixup::create(16, expr, fixup_NPU_branch) — the first argument is the byte offset of the fixup within the instruction word. By anchoring at 16 (the start of the 8-byte imm field), the ELF writer sets r_offset = instruction_start + 16, pointing directly at the bytes that the linker will patch. applyFixup receives Data already pointing at the imm field, so it writes 8 bytes at offset 0 within Data.
If offset 0 were used, r_offset would point at the stream-type byte, not the imm field. The linker would overwrite opcode/rd/rs1 bytes instead of the immediate — corrupting the instruction.
EM_NPU = 315, defined after EM_LOONGARCH
The ELF machine number 315 (0x13b) was chosen to avoid collisions with all known standard ELF targets. It is added after EM_LOONGARCH = 258 in llvm/include/llvm/BinaryFormat/ELF.h. The enum block for NPU relocations is also in ELF.h, pulling definitions from llvm/include/llvm/BinaryFormat/ELFRelocs/NPU.def via the standard ELF_RELOC macro pattern.
Custom non-standard value for an experimental target. Not registered with the official ELF spec — this is a research/prototyping backend. A production target would apply for a number from the ABI committee.
Vector ISA uses separate engine scalars (s0–s31), not GPRs (x0–x31)
The vector core has its own scalar register file (engine scalars s0–s31) entirely separate from the control core's GPRs (x0–x31). Engine scalars serve as loop counters, vector-length holders, reduction targets, and memory base addresses within vector kernels. The LLVM vector register info defines these as a separate register class EngineScalar with its own allocation order.
The vector and control cores execute asynchronously — GPRs are not visible to the vector engine. Using a separate register file matches the hardware architecture and avoids cross-domain register conflicts at the ISA level.

Status

Known gaps

The backend is functional for single-basic-block functions and produces correct ELF object files. The following areas are not yet implemented.

insertBranch not implemented in NPUInstrInfo
Multi-basic-block functions that trigger the BranchFolding pass (which calls TargetInstrInfo::insertBranch() to tail-merge blocks) crash with: Target didn't implement TargetInstrInfo::insertBranch! The ELF relocation test works around this by using a single-block function.
T_CONV and T_POOL are stubs
Convolution and pooling are marked as stubs in the simulator (npu.c). The LLVM backend defines their opcodes in the encoding table but there are no corresponding @llvm.npu.conv / @llvm.npu.pool intrinsics or lowering paths. These should be built from vector-core primitives.
No MLIR dialect or IREE integration
llvm_lowering.md sketches a design for lowering from MLIR to NPU: control core → scalar IR + RISC-V-style backend; tensor engine → target intrinsics over an opaque target("npu.tile") type (cf. x86 AMX); vector core → native LLVM vector IR + intrinsics. None of this exists yet — the LLVM backend is reachable only via direct @llvm.npu.* intrinsics.
T_QUANT / T_DEQUANT intrinsics missing
The simulator defines quantization opcodes (cop_t values 43, 44). The LLVM backend encoding table includes them, but no @llvm.npu.quant / @llvm.npu.dequant intrinsics are declared and no lowering patterns exist. Integer/quantized lanes are currently modeled in the simulator as float (VCVT rounds/clamps) — fine for functional checks, not bit-exact int8.
No ELF symbol versioning or section grouping
The ELF writer produces minimal output: .text, .note.GNU-stack, .symtab, .strtab, and .rela.text (when relocations exist). No .eh_frame, no COMDAT groups, no debug info (.debug_info / DWARF). A production linker would require at minimum .eh_frame for stack unwinding.
